Le plugin OnlyOffice « Données du compte rendu »

Comment il a été construit, packagé et déployé, comment il dialogue avec l'éditeur OnlyOffice et avec le serveur Spring Boot (REST + GraphQL), et comment les données du dossier patient arrivent jusque dans le document. État du code : branche feature/contrat-champs-fusion, novembre 2026.

0.Comment lire ce document

Les questions posées ont été regroupées dans l'ordre où l'on en a besoin : d'abord où le plugin s'insère, puis ce qu'il faut pour en écrire un, comment il est livré, et enfin comment il parle à l'éditeur puis au serveur.

« Où se situe le plugin ? »Vue d'ensemble des quatre composants et des trois origines web. « Que faut-il pour développer un plugin ? »Connaissances, outils, contraintes propres à OnlyOffice. « Comment est-il packagé et déployé ? »Dossier statique Spring, déclaration dans la configuration de l'éditeur, CORS. « Comment communique-t-il avec OnlyOffice ? »executeMethod, callCommand, content controls et tags. « Comment interagit-il avec le backend ? »REST pour la fiche et la validation, GraphQL pour les données. « Comment les données sont-elles chargées ? »schema.graphqls → introspection → modèle → arborescence et réglages ; liaison → requête unique → rendu. « Des exemples de requêtes ? »Introspection, en-tête patient, requête compilée et sa réponse, archive réelle.

1.Architecture d'ensemble

Le plugin n'est pas une application à part : c'est une page web dans une iframe, affichée par l'éditeur OnlyOffice dans un onglet latéral droit. Il y a trois niveaux d'imbrication dans le navigateur et deux origines web différentes (:8081 pour Spring, :8080 pour le Document Server).

Le plugin et la page hôte sont servis par Spring : ils partagent l'origine :8081, ce qui permet au plugin d'appeler /graphql sans CORS et de lire window.top.PocCr.

ComposantRôleOù dans le dépôt

Document ServerÉditeur Word en ligne, SDK des plugins, conversion, appel du callback de sauvegardedocker-compose.yml (image onlyoffice/documentserver)

2.Prérequis pour développer un plugin OnlyOffice

Connaissances

  • HTML / JavaScript côté navigateur. Le plugin est une page web ordinaire.
  • ES5 pour tout code exécuté dans le document (callCommand, scripts des content controls) : il est sérialisé en texte puis évalué par l'éditeur.
  • API des plugins OnlyOffice : objet window.Asc.plugin, executeMethod, callCommand, Asc.scope.
  • API Document Builder (Api.CreateParagraph, Api.CreateTable, Api.CreateInlineLvlSdt…).
  • Content controls OOXML (w:sdt) : tag, alias, verrou, en ligne / bloc.
  • Côté données : GraphQL (requêtes, alias, introspection).

Outils

  • Un Document Server qui tourne : docker compose up -d (port 8080). Sans lui, impossible de voir l'onglet ; les tests Node ne font que simuler l'éditeur.
  • Un serveur web pour servir le plugin : ici Spring Boot (mvn spring-boot:run, port 8081).
  • Node ≥ 20 pour les tests node:test du plugin (le Node 16 par défaut du poste est trop ancien).
  • JDK 21 + Maven pour le serveur.
  • Outils de développement du navigateur : choisir le contexte de la console sur l'iframe du plugin (voir §10).

Contraintes à connaître avant d'écrire la première ligne

  • Pas de alert / confirm / prompt : ils bloquent l'éditeur entier. Le POC confirme la validation en deux clics (demanderValidation puis valider).
  • Code passé à callCommand = ES5, sans fermeture : la fonction est transformée en texte, elle ne voit pas les variables du plugin. Les données passent par Asc.scope.
  • CORS : le manifeste est lu depuis l'origine du Document Server. Sans en-têtes CORS sur /plugin/**, l'onglet n'apparaît jamais, sans message d'erreur.
  • Le conteneur ne voit pas localhost du poste : le Document Server joint Spring par host.docker.internal, et ALLOW_PRIVATE_IP_ADDRESS=true est nécessaire.
  • Épingler la version du Document Server : l'API varie d'une version à l'autre (cf. l'ordre des arguments de Api.CreateTable, §5).
  • JWT : désactivé dans le POC (JWT_ENABLED=false). En production, la configuration de l'éditeur et les callbacks doivent être signés.

3.Anatomie du plugin

Un plugin OnlyOffice est un dossier de fichiers web qui suit une structure attendue par l'éditeur : un manifeste, une page d'entrée, du code qui utilise le SDK, des icônes. Cette section décrit chaque élément tel que la documentation OnlyOffice le définit, puis la façon dont le POC l'utilise.

Documentation officielle OnlyOffice : par où commencer
  • Vue d'ensemble des plugins et démarrage rapide
  • Configuration (config.json), avec ses pages types, variations, point d'entrée, icônes, localisation, styles et thèmes
  • Interagir avec les éditeurs : objet Asc.plugin, appeler des méthodes, appeler des commandes, s'abonner aux événements
  • Exemples proches de ce POC : tags de content controls, contenu des content controls, navigation entre content controls

3.5 Les modules JavaScript

OnlyOffice n'impose aucune organisation du code. Dans le POC, chaque fichier est une IIFE qui s'expose deux fois : sur window pour le navigateur, et par module.exports pour les tests Node. Il n'y a ni bundler ni dépendance npm.

(function (racine) {

4.Packaging et déploiement

En une phrase Le plugin n'est ni compilé ni zippé : c'est un dossier statique embarqué dans le jar Spring Boot, servi sous /plugin/, et signalé à l'éditeur, document par document, par la configuration que Spring génère.

4.1 Packaging : un dossier de ressources statiques

Tout ce qui se trouve sous src/main/resources/static/ est copié dans le jar par mvn package et servi à la racine par Spring MVC. Le plugin est donc disponible à http://localhost:8081/plugin/config.json, …/plugin/index.html, etc. Une nouvelle version du plugin = une nouvelle version du serveur. Pensez à incrémenter version dans config.json et à vider le cache du navigateur si l'onglet ne se met pas à jour.

Ce choix a un avantage décisif : le plugin et /graphql ont la même origine. Aucune configuration CORS n'est nécessaire pour les appels de données.

4.2 Déploiement : déclaration dans la configuration de l'éditeur

Référence : editorConfig.plugins (autostart, pluginsData, options, disable).

À l'ouverture d'un document, la page hôte demande sa configuration à Spring (ControleurDocuments.configuration), puis la passe à new DocsAPI.DocEditor. C'est cette configuration qui déclare le plugin :

5.Comment le plugin dialogue avec OnlyOffice

Le plugin ne touche jamais au DOM de l'éditeur : il vit dans une autre iframe. Le SDK plugins.js échange des messages (postMessage) avec l'éditeur. Le plugin dispose de trois leviers.

5.1 Cycle de vie

window.Asc.plugin.init = function () {       // appelé quand l'iframe et le SDK sont prêts
    brancherInterface();
    chargerFiche()                             // REST : quel document, quel patient
        .then(G.chargerSchema)                 // GraphQL : introspection
        .then(function (modele) { …; return controlerPatient(); })
        .then(verifierValidation)
        .catch(afficherErreur);
};
window.Asc.plugin.button = function () { this.executeCommand('close', ''); };

5.2 Canal ① : l'API « méthodes »

Le POC enveloppe executeMethod dans une promesse :

5.3 Canal ② : callCommand et Document Builder

Références : callCommand · Office JavaScript API (texte) · CreateInlineLvlSdt · ApiInlineLvlSdt (SetTag, SetLock) · InsertContent

Utilisé pour ce que l'API « méthodes » ne sait pas faire : les contrôles en ligne (dans une phrase). La fonction est sérialisée et exécutée dans le contexte du document : ES5 seulement, aucune variable du plugin accessible. Les données passent par Asc.scope.

function commande(fonction, donnees) {
    return new Promise(function (ok) {
        window.Asc.scope.donnees = donnees;
        window.Asc.plugin.callCommand(fonction, false, true, ok);   // isClose=false, isCalc=true
    });
}

// Insère un contrôle en ligne à la position du curseur.
function insererEnLigne(controle) {
    return commande(function () {
        var d = Asc.scope.donnees;               // { texte, tag, alias, lock }
        var cc = Api.CreateInlineLvlSdt();
        var run = Api.CreateRun();
        run.AddText(d.texte);
        cc.AddElement(run, 0);
        cc.SetTag(d.tag);                        // la liaison JSON
        cc.SetAlias(d.alias);                    // visible au survol
        cc.SetLock(d.lock);                      // "contentLocked"
        var p = Api.CreateParagraph();
        p.AddInlineLvlSdt(cc);
        Api.GetDocument().InsertContent([p], true);   // true = fusion dans le paragraphe courant
    }, controle);
}

5.4 Canal ③ : un script dans un contrôle bloc

Références : InsertAndReplaceContentControls · Api.CreateTable · GetRowsCount · valeurs de Lock

Pour un tableau, InsertAndReplaceContentControls reçoit un Script Document Builder sous forme de chaîne, construite par rendu.js. Les données y sont injectées avec JSON.stringify, jamais par concaténation brute :

ecrireControles([{
    Props: { Tag: '{"v":2,"r":"patient","p":"…","c":"observations",…}',
             Alias: 'Observations (biologie, constantes) (categorie=BIOLOGIE)',
             Lock: 0,                          // 0 = contenu verrouillé, contrôle supprimable
             InternalId: '…' },                // absent → insertion au curseur
    Script: 'var entetes = ["Examen","Valeur","Unité"]; var lignes = [["HbA1c","7.2","%"]];' +
            'var t = Api.CreateTable(entetes.length, lignes.length + 1);' +
            'if (t.GetRowsCount() !== lignes.length + 1) t = Api.CreateTable(lignes.length + 1, entetes.length);' +
            '…; Api.GetDocument().InsertContent([t]);'
}]);

5.5 Le content control comme support de la donnée

Chaque donnée insérée est un content control. Son tag porte la liaison (ce qu'il faut demander à GraphQL), son contenu porte la valeur affichée. Le document se suffit à lui-même : à la réouverture, le plugin relit les tags et sait tout rafraîchir.

UsageType de contrôleÉcrit parVerrou en éditionVerrou après validation
Valeur, valeurs jointes, accorden ligne ("m":"i")callCommand"contentLocked""sdtContentLocked"
Liste d'objetsbloc (tableau)InsertAndReplaceContentControlsLock: 0Lock: 1

En édition, le médecin ne peut pas retoucher la valeur à la main mais peut supprimer le contrôle. Une fois validé, ni l'un ni l'autre.

5.6 Deux pièges rencontrés sur le Document Server 10.0

Ordre des arguments de Api.CreateTable La version testée attend (lignes, colonnes), l'inverse de la documentation. Seuls les tableaux 2 × 2 fonctionnaient. Le script vérifie GetRowsCount() et recrée le tableau si besoin.
Un contrôle bloc verrouillé ignore son remplacement Avec Lock 0 ou 1, InsertAndReplaceContentControls ne remplace pas le contenu et ne signale rien. ecrireControles déverrouille d'abord les contrôles visés (SetLock("unlocked") via callCommand), puis le remplacement repose le verrou demandé.

6.Comment le plugin interagit avec le backend

Le plugin utilise fetch avec des chemins relatifs. Servi par Spring, il est dans la même origine que l'API : pas de CORS, pas de configuration d'URL.

REST : le contexte du document

Ce que le plugin doit savoir avant de demander des données : quel document, quel patient, déjà validé ou non.

GraphQL : les données

6.1 Savoir quel document est ouvert

L'éditeur ne transmet pas au plugin l'identité du document. Le POC passe par la page hôte, de même origine :

// page hôte, à l'ouverture
window.PocCr.documentCourant = nom;

// plugin (code.js)
function nomDocument() {
    try { return window.top.PocCr && window.top.PocCr.documentCourant; }
    catch (e) { return null; }                 // autre origine : accès refusé
}

Raccourci de POC. Piste documentée : editorConfig.plugins.options transmet des paramètres à un plugin désigné par son guid (identifiant du document, jeton…). Non essayé dans le POC.

6.3 Le client GraphQL du plugin

Volontairement minimal (graphql.js) : un POST JSON, et les erreurs GraphQL deviennent des exceptions.

function executer(requete, variables) {
    return fetch('/graphql', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ query: requete, variables: variables || {} })
    }).then(function (reponse) {
        if (!reponse.ok) throw new Error('GraphQL HTTP ' + reponse.status);
        return reponse.json();
    }).then(function (corps) {
        if (corps.errors && corps.errors.length) throw new Error(corps.errors.map(…).join('\n'));
        return corps.data;
    });
}

6.4 Côté serveur : résoudre sans N+1

  • ControleurDossierPatient et ControleurDocument (Spring for GraphQL) résolvent les champs.
  • Les champs à arguments (observations, traitements) passent par des DataLoaders dont la clé contient le filtre : deux alias observations(categorie: BIOLOGIE) et observations(categorie: CONSTANTE) donnent deux clés, regroupées par filtre en SQL.
  • sejours et sejourCourant partagent un chargeur : demander les deux = une requête SQL.
  • Racine document : quatre chargeurs (acteurs, professionnels, coordonnées, établissements).

7.4 Étape 2 : analyserSchema réduit la réponse en modèle

La réponse brute est trop verbeuse pour être parcourue à chaque clic. analyserSchema(types) (graphql.js) la transforme une fois pour toutes :

  1. Filtrer les types : seuls les types OBJECT sont gardés. Query et les types techniques __Schema, __Type… sont écartés.
  2. Dérouler chaque type (derouler) : retirer les NON_NULL et les LIST et retenir s'il y avait une liste. [Observation!]! devient { kind: "OBJECT", nom: "Observation", liste: true }.
  3. Libellé = description, sinon le nom du champ. Les champs id sont exclus.
  4. Enums : pour un champ ou un argument enum, rattacher la liste des valeurs (valeursEnum) et leurs descriptions (libellesEnum), lues dans le type enum correspondant.
  5. Valeurs par défaut (lireDefaut) : "\"P3M\"" devient "P3M", "false" devient false, et "PROFESSIONNELLE" reste tel quel.
  6. Racines : chercher patient et document parmi les champs de Query (y compris ceux ajoutés par extend type Query) et noter leur type.

Règles de construction

  • Nœud = { racine, champs: [Champ…] }. Le chemin du tag (c) est la suite des noms de ces champs.
  • Nature (natureDuNoeud) : valeur (scalaire ou enum, feuille), objet (dépliable), liste (dépliable et insérable en tableau).
  • Badge « liste » si liste: true, badge « réglable » si le champ a des arguments (leurs libellés sont dans l'info-bulle).
  • Pas de cycle : un champ objet dont le type figure déjà parmi les ancêtres n'est pas proposé.
  • Profondeur maximale : 7 segments.
  • Navigation au clavier (flèches, Entrée) : l'arbre suit le motif ARIA tree.

7.7 Étape 5 : le modèle comme garde-fou et comme guide de mise en forme

Avant chaque requête (aperçu, insertion, rafraîchissement, validation), L.analyser relit chaque tag contre le modèle, pas contre ce que l'onglet a affiché :

  • chaque segment du chemin doit respecter la syntaxe d'un nom GraphQL, exister dans le type courant, et être un objet s'il n'est pas le dernier (resoudreChemin) ;
  • chaque argument doit exister sur le champ concerné. Une valeur d'enum doit appartenir à valeursEnum, un Boolean, Int ou Float est converti, une chaîne passe par JSON.stringify (formaterArgument) ;
  • une colonne inconnue (tag ancien, schéma modifié) est ignorée. Sans k, les colonnes par défaut viennent du modèle (colonnesParDefaut).

Le même modèle guide la mise en forme (rendu.js) :

  • en-têtes de tableau et alias des contrôles = libellés du chemin (« Observations (biologie, constantes) › Examen ») ;
  • une valeur d'enum est remplacée par sa description (FEMININ devient « Féminin »). Une chaîne d'un champ non enum (« MARTIN ») n'est jamais reformatée.

8.Exemples de requêtes GraphQL

Toutes ces requêtes peuvent être rejouées dans GraphiQL (serveur lancé).

8.1 Introspection (démarrage)

Envoyée une fois. Elle remonte les descriptions (les libellés), les arguments et leurs valeurs par défaut, les valeurs d'enum.

query Introspection {
  __schema {
    types {
      name kind description
      fields {
        name description
        args { name description defaultValue type { kind name ofType { kind name ofType { … } } } }
        type { kind name ofType { kind name ofType { … } } }
      }
      enumValues { name description }
    }
  }
}

L'introspection doit rester active (spring.graphql.schema.introspection.enabled: true) : sans elle, l'onglet est vide.

8.3 La requête unique du document

Supposons un compte rendu contenant six contrôles. Leurs tags :

c5  {"v":2,"r":"document","c":"signatairePrincipal.medecin.adresse.ville",

L.construireRequete les compile en une seule opération DonneesDocument (mise en forme ici pour la lecture ; le plugin l'envoie sur une ligne) :

query DonneesDocument($id: ID!, $doc: ID!) {
  patient(id: $id) {
    c0: nom
    c1: sexe
    c2: sejourCourant { service }
    c3: observations(categorie: BIOLOGIE, depuis: "P3M") { libelle valeur unite }
    c4: traitements(actifsSeulement: true) { __typename }    # accord en nombre : seul le compte compte
  }
  document(id: $doc) {
    c5: signatairePrincipal { medecin { adresse(type: PROFESSIONNELLE) { ville } } }
  }
}

variables : { "id": "<patientId de la fiche>", "doc": "<id du document>" }
  • Les alias permettent de demander plusieurs fois le même champ avec des filtres différents (par exemple observations(categorie: BIOLOGIE) et observations(categorie: CONSTANTE)).
  • Seules les variables des racines utilisées sont déclarées : un document sans liaison document n'envoie que $id.
  • La liaison document ne porte jamais d'identifiant : c'est toujours le document courant.
  • Les chaînes passent par JSON.stringify, les enums sont vérifiés contre les valeurs du schéma.

9.Validation et scellement : le serveur fait foi

À la validation, le plugin n'envoie pas les valeurs qu'il affiche : il envoie la requête. Le serveur la réexécute dans son propre moteur GraphQL, avec des variables qu'il impose, fige la réponse et c'est elle que le plugin écrit.

// plugin (code.js) — extrait de valider()
var requete = L.construireRequete(instance.liaisons, etat.modele);
api('POST', '/validation', { patientId: instance.patientId, requete: requete })
  .then(…)
  .then(function (validation) {
      // Les valeurs écrites sont exactement celles figées côté serveur.
      var valeurs = L.valeurs(instance.liaisons, JSON.parse(validation.donneesJson));
      return ecrireValeurs(instance, valeurs, VERROU_FIGE, true)
          .then(function () { return methode('SetEditingRestrictions', ['readOnly']); })
          .then(function () { afficherEtatValide(validation); });
  });
  • Le serveur refuse toute opération autre que DonneesDocument et impose $id / $doc : le plugin ne peut pas faire figer les données d'un autre patient.
  • Le callback répond toujours {"error":0}, même quand il ignore une sauvegarde : sinon OnlyOffice réessaie en boucle.
  • À la réouverture, la configuration passe en mode: "view" et le plugin (isViewer) affiche la date, le valideur et les empreintes.

11.Limites connues et points à confirmer

Raccourcis de POC

  • URL du SDK codée en dur dans plugin/index.html (http://localhost:8080/sdkjs-plugins/v1/plugins.js) : à paramétrer par environnement.
  • Document courant lu par window.top.PocCr : suppose la même origine ; à remplacer par un identifiant transmis dans la configuration de l'éditeur.
  • JWT désactivé, pas d'authentification, valideur = signataire principal, utilisateur affiché « Dr POC ».
  • Introspection ouverte en permanence ; tout le schéma est proposé (filtrage par rôle ou directive à prévoir).

API OnlyOffice non encore confirmées une par une

  • Sémantique exacte de Lock (0/1) dans l'API « méthodes ».
  • Position du curseur après insertion en ligne (risque de rester dans un contrôle verrouillé).
  • Longueur de tag conservée par Word au round-trip.
  • Toutes les méthodes Document Builder utilisées : CreateInlineLvlSdt, RemoveAllElements, GetInternalId, GetClassType, SetTableBorder*…
